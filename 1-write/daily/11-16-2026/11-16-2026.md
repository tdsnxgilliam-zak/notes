## Shared context (what the update agent does today)

- Update path lives under Spec 06 (`src/spec-06/update-request/…`). Case gate `decideUpdateCase` returns:
  - **A** — classification aligned with current action → update that action (note / status / files).
  - **B** — open action, classification changed → mutate / retarget open action.
  - **C** — current action is **COMP** *and* classification differs → build `addServiceBody` and `POST …/request/{requestNo}/services` (new service line + new action).
- Status updates go through `PUT /api/rcs/internal/action/status` (`statusType`: `NEW` \| `WORK` \| `HOLD` \| `CANC` \| `COMP` \| …). RC **rejects** illegal transitions via `ActionService.validateStatusTransition` (prod example: `COMP` → `HOLD`).
- Mailbox resolution for Cisco sales: `ciscoSalesIdpMailboxMap` (`idpCode` → mailbox) in `src/spec-02/…/load-mailbox-map.js`.
- Folder moves: prefer IDP helper `WE_ScriptHelper.idpMoveDocument` (display folder name + `documentPath` + `idpCode`), or Spec 07 MCP `graph-mailbox-move` (config-driven folder names; non-blocking on failure).

## 1. Fallback — move exhausted failures to `IDP Failed`


The below technical decision works and will be implemented

### Problem

When the workflow keeps failing (e.g. Request Central outage), including paths that would otherwise be Needs Review, the mail can leave no durable operator-visible place. Requirement: move it to Outlook folder **`IDP Failed`** on the correct mailbox.

### What must be explained / decided before coding

| Gap                                      | Answer from docs (or still open)                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Target folder name                       | **`IDP Failed`** — IDP Portal default for `userPreference.failedDoc.moveTo` ([IDP-v1.2.3 failed-doc design](https://confluence.synnex.com/pages/viewpage.action?pageId=792321851); patch default `DEFAULT_FAILED_DOC_MOVE_TO = "IDP Failed"`).                                                                                                           |
| Why leave Inbox                          | IDP rescans Inbox every cycle; failed mail left in Inbox is re-queued and starves new mail. Failures must be moved out ([same page](https://confluence.synnex.com/pages/viewpage.action?pageId=792321851)).                                                                                                                                              |
| Which mailbox                            | The mailbox for the event’s **`idpCode`**, via `ciscoSalesIdpMailboxMap` (not a hard-coded single inbox). Precedence losers already skip processing; only the winning/current `idpCode` mailbox is in scope.                                                                                                                                             |
| How to move                              | **Recommended:** `WE_ScriptHelper.idpMoveDocument({ idpCode, destinationPath: "IDP Failed", documentPath })` per [04 IDP API](https://confluence.synnex.com/pages/viewpage.action?pageId=716642192). Alt: MCP `graph-mailbox-move` with config folder display name `IDP Failed` ([spec-07](../../xidea-tickets/specs/spec-07-mcp-integration-layer.md)). |
| Related outcome folders (do not confuse) | Per [RQCEN-381](https://confluence.synnex.com/pages/viewpage.action?pageId=710499711): success create → `IDP Archive`; invalid → `IDP Invalid`; duplicate → `duplicatedmail`. Failure terminal → `IDP Failed` (not Archive). Optional future: transient → `IDP Retry` (IDP Portal schedule); **this issue asks for Failed**, not Retry.                  |
| When to fire                             | After retries are exhausted / non-retryable terminal failure — including when Needs Review / RC review create also cannot complete. Spec 08: folder move is **not** the review mechanism; it is a **visibility fallback** when automation + review cannot land the work.                                                                                 |
| Open                                     | Exact trigger set (which `Workflow_*` states / error codes), interaction with IDP Portal `failList` auto-move (avoid double-move), and whether Needs Review *success* still archives elsewhere.                                                                                                                                                          |

## 3. COMP → other status — create a new action instead

### Problem

Matched request has an action in **`COMP`**. Follow-up email (same classification) still drives `updateActionStatus` toward `WORK` / `HOLD`. RC throws:

`Transition from current status [COMP] to target status [HOLD] is not allowed`

(`ActionService.validateStatusTransition` — see [Request Central Integration APIs](https://confluence.synnex.com/pages/viewpage.action?pageId=759936532): “Status transition must be allowed by workflow.”)

### What must be explained / decided before coding

| Gap                         | Answer from docs (or still open)                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Allowed fix                 | **Do not** transition off `COMP` with normal status update. **Create a new action** on the **same request**, even when service/action type is the **same**.                                                                                                                                                                                                                                                                                          |
| Wrong approach              | Do **not** use Superuser **Status Reset** (`COMP`→`HOLD` bypass) for triage automation ([RQCEN-427 AD](https://confluence.synnex.com/pages/viewpage.action?pageId=770476549) — maintenance-only, `RC_SUPERUSER`).                                                                                                                                                                                                                                    |
| Current bug shape           | `decideUpdateCase`: same service pair → **Case A** (“aligned”) even when status is `COMP`, so the pipeline updates status on the completed action. Case **C** only runs when classification **differs**. Issue requires Case-C-like **new action** also when classification is **the same** and status is `COMP`.                                                                                                                                    |
| Which create API            | Prefer existing Case C path: `POST /api/rcs/internal/request/{requestNo}/services` (`addServiceBody` / `addRcService`) which creates workflow actions for the brand/service. Alt: `POST …/request/{requestNo}/action` adhoc ([RC Integration APIs §5](https://confluence.synnex.com/pages/viewpage.action?pageId=759936532); KB RC-066). Confirm with RC whether same `serviceTypes` on an already-served brand is allowed via add-service vs adhoc. |
| New action initial status   | Adhoc defaults to **`NEW`**. Catalog may then suggest `WORK`/`HOLD` for the **new** action only — never against the old `COMP` row.                                                                                                                                                                                                                                                                                                                  |
| Other terminal statuses     | Open: treat `CANC` / `APPR` / `DENY` like `COMP` (new action) or only `COMP`?                                                                                                                                                                                                                                                                                                                                                                        |
| Same request vs new request | Issue says create a **new action** (same request), not a new request — keep match on existing `requestNo`.                                                                                                                                                                                                                                                                                                                                           |

## Cross-cutting explanations (all three issues)

1. **Mailbox selection:** always `idpCode` → `ciscoSalesIdpMailboxMap`; use that mailbox’s folders.
2. **Move semantics:** folder display names from config; create folders in each Phase 1 mailbox before UAT; move failures are logged and must not crash a path that already decided “no RC write.”
3. **Visibility vs review:** Spec 08 — RC review queue is canonical for human work; Outlook folders are secondary. Fallback/ECExpress folders are for **operator visibility / non-RC filing**, not a substitute review system.
4. **Idempotency:** do not create duplicate RC tickets on retry; folder move may be retried safely if already moved.
5. **Observability:** log `recordId`, `idpCode`, mailbox, destination folder, decision reason (`fallback_idp_failed` / `ecexpress_unmatched_folder` / `comp_create_new_action`).
